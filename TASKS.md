- [ ] **B1 — Back-nav crash after handover code → Done (BUG, highest priority)** — after generating/viewing a pickup or delivery code and tapping **Done**, pressing back exits the whole app instead of returning to the previous screen. Almost certainly a `context.go()` where it should be `context.push()`/`pop()` — `go()` *replaces* the navigation stack, so there is nothing left to pop and Android's back gesture falls through to the launcher. Suspects: `payment_screen` → `context.go('/handover/code/<mid>?kind=pickup')`, the `Done` button in `handover_code_screen.dart`, and the `live_event_router` deep-links. Fix: route forward with `push` and make `Done` `pop()` back to the match/request detail (or `go` to an explicit parent that has a real stack). Repro on a physical device — the emulator back button can mask it.
- [ ] **B2 — Stop telling the user to regenerate the handover code** — the code is issued **once** and stored server-side; the 2026-07-20 audit (below) confirmed every *re-view* path already reads without rotating, so the backend is correct. The problem is purely presentational: the UI still surfaces a **Regenerate** affordance and copy that implies the code is transient, which makes users think they must re-generate (and an accidental tap *does* rotate the code, invalidating what the counterparty already wrote down). Fix: remove/de-emphasise the Regenerate button from the normal path — show the stored code as a settled fact ("Your pickup code", persistent). If a recovery escape hatch is still wanted, bury it behind a confirm dialog that spells out that the old code stops working. Do NOT change the idempotent auto-issue logic; it is already right.
- [ ] **B3 — Persist the session + remembered role; no re-login and no re-picking sender/traveler each launch** — user should not sign in every time, nor re-choose sender vs traveler on every launch. Refresh tokens + role hydration already exist (`auth_storage.dart`, the role-hydration boot gate), so this is likely (a) the refresh token not being used to silently restore the session on cold start, and/or (b) the router still sending a signed-in user through `/role`. Fix: on boot, attempt a silent refresh before deciding the redirect, and skip `/role` entirely when a saved role exists (only ever show it on true first run for a `both` account). Verify by force-closing and reopening the APK.
- [ ] **B4 — Confirm-password field on sign-up** — currently one password box; a typo silently creates an unreachable account. Add a "Confirm password" `AppInput` with inline mismatch validation client-side. Server-side is optional (the client is the right place for a typo guard) but keep the existing password-strength rules. Mobile-only change.
- [ ] **B5 — Let users delete their own trips and parcels** — no way to remove a flight or a parcel request once created. Check what already exists: parcels/trips have full CRUD per CLAUDE.md §0, and there are `parcel.cancelled` / `trip.cancelled` channels, so DELETE (or a cancel action) may already be server-side — confirm before writing endpoints. Mobile needs the affordance: a destructive action on `my_requests_screen` / the traveler's trip list, behind a confirm dialog. **Guard rail:** must NOT be deletable once money or a match is involved — block when the parcel/trip has an accepted offer, a captured payment, or a match in `in_transit`/`completed`. Prefer soft-cancel over hard delete so history and the wallet ledger stay intact.
- [ ] **B6 — Apply directly to a suggested trip from an existing parcel (no re-filling the form)** — after a sender creates a request, the app shows matching flights but they are read-only; the sender has to re-enter all the parcel info to actually apply. The parcel already exists, so applying should just create the Match+Offer against it. Fix: make each suggested-trip card actionable, passing the existing `parcelId` (the plumbing is there — `/sender/new?traveler=<id>` already targets a traveler, and `find_travelers_screen` creates matches). Route to a lightweight "apply with this parcel — your price?" sheet rather than the full `make_request_screen`. This is the single biggest flow win on the list.
- [ ] **B7 — Counter-offer direction is asymmetric BY DESIGN — verify, don't "fix"** — Islam's model, in his words: a **traveler** browsing parcels sees the sender's price and either applies or doesn't (no counter needed — not applying *is* the rejection). A **sender** who searches for a traveler and applies with a price sends a notification the **traveler can counter** with their desired price. Note this is exactly the existing `targeted-only` rule (`CounterOfferView` 409s on broadcast requests; `canCounter = parcel.targetTravelerId != null`), so the backend already encodes it. What to check: (a) the traveler actually *sees the sender's proposed price* prominently in the notification/match detail, not buried; (b) the Counter control is visible to the traveler on a targeted request; (c) the traveler's own apply-to-carry flow does not confusingly offer a "counter" on a broadcast parcel. Likely a copy/visibility task, not a logic change — confirm against `match_detail_screen` before touching `matching/views.py`.
