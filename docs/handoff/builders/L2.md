## 1. Your job

Two generations of data shapes live side by side in the server. Requests and journeys carry a
`schema_version`, and matching, discovery, pricing and finance branch on it. Only the current
shape can be created today. Remove the old shapes, their models and their branches. No result
for current data may change.

## 3. How

1. **Inventory first**, as plan section 3.5 says. An item with a live reader is not old,
   whatever its name: leave it and list it.
2. **Show that no old row can be created.** For requests and for journeys: every write path
   stores the current version, shown by reading the paths and by a test.
3. **Differential test before any change to matching.** Keep a frozen copy of
   `evaluate_compatibility` and of each other function whose branches you remove. A test
   generates current-shape requests and journeys across the cases the existing matching tests
   use, and compares the full result of the old and the new function: checks, rejection codes,
   limitations, order. It must pass at every commit. In the last commit, delete the frozen copies
   and that test.
4. Remove the branches. Then drop each column that can now hold only one value, with its
   constraint, in a migration of its own app. Then delete the old models.
5. Do not restructure `evaluate_compatibility`. When the old branches are gone, report its new
   length and whether it still mixes separate jobs. The planner decides what follows.

## 4. What is not yours

The dead apps (L1). The legacy money markers and `economics_version` (L3). Any change to a
matching, pricing or money result for current data: if you find one, stop and ask.

## 5. Proof

- The differential test, green at every commit until its removal.
- The whole suites are green. Each removed or rewritten test is listed with its reason. A test
  that set an old version to test a current rule is rewritten to the current shape, not removed.
- `backend/contracts/sql/schema.sql` changes only by the listed tables, columns and constraints.
- Each removed payload field (`legacy_trip_id`, `schema_version` where it was sent) is searched
  in `mobile/lib`. If the app reads one, leave the field out of this brief and tell the lead.
