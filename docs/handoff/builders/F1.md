## 2. What you build

Paths are under `backend/monolith/`.

**F-C1. The freeze** (`apps/finance/payout_profiles.py`, `set_preference`).
While `current_creation(method)` is prepared, committed or unknown, a write that would change the
euro method's `enabled` or its country is refused with the stable code `payout_setup_in_progress`
(409), translated. The check runs after `_method` returned the locked method row and before any
write. A write that changes neither, and any DZD write, is not refused. The PATCH and the
single-currency POST both call `set_preference`, so there is one check.

**F-C2. A call whose rows changed starts again, once** (`apps/finance/payout_accounts.py`:
`ensure_account`, `start_onboarding`, `_require_unchanged`, `_record_account`, `_bind`).
No lock is held across the Stripe call, so two onboarding calls can overlap. Both send the same
idempotency key, so Stripe creates one account. When a call finds that a conditional update
changed zero rows, or that the method's current version is no longer the one it planned for, it
reads the rows again and runs once more from the top. If the rows changed again, it answers
`payout_preference_changed`. It never answers from what it saw before the Stripe call.

**F-C3. When the freeze ends.**

- An account is recorded and bound: the freeze ends.
- Stripe refused the creation request itself: the operation is `failed`, as today, and the freeze
  ends.
- An unclear answer inside `IDEMPOTENT_REPLAY_SECONDS`: the freeze stays, and the next onboarding
  call replays the same key, as today.
- **Past the window** (`_ask_stripe`, call `search`): `find_account_by_metadata` reads every page
  of the accounts created between the operation's first request minus one minute and that request
  plus 25 hours (`created[gte]`, `created[lte]`, then `starting_after` while `has_more`). One
  match is recorded and bound. **No match on a complete listing ends the operation as `failed`**,
  so the restart of F-C2 creates a fresh attempt with a new key. More than one match, an error, or
  more than twenty pages leaves it `unknown`, as today, and is logged.
- With that, nothing answers "requires Finance review" any more. Delete
  `AccountCreationUnresolved`, `CREATION_NOT_FOUND`, the `stripe_account_unresolved` code and its
  strings, unless a search shows another live use. **[Guess]** Stripe's account list by creation
  time is complete 23 hours after the request. Confirm it in Stripe's documentation of the list
  call. If it does not hold, stop and ask.

**F-C4. The read model** (`stripe_setup_projection`, `onboarding_refusal`,
`payout_profile_api.py`, `payout_mobile.py`). While the freeze holds, the euro options are not
changeable, with `payout_setup_in_progress`, and "continue setup" is offered. No action is offered
that its write refuses every time.

**F-F. Eligibility on the locked row.** One function answers "may this account write payout setup
now": active, not banned, a traveler role, a confirmed email. It replaces `holds_payout_setup` and
the separate email checks in the views. It is called on the user row that `_method` and
`_plan_onboarding` already lock, and once more in the last transaction before the hosted link is
returned. A creation that was already committed when a ban arrives may still be recorded, so the
account at Stripe is known to the database. It is not bound and no link is handed out.

**F-G. One answer per response.** A payout GET computes the euro actions once and gives the same
values to both serializers (`payout_profile_api.py` and `payout_mobile.py` compute them
separately today). The GET's reads run inside `consistent_read()`
(`apps/finance/control_plane/snapshot.py`). A write's response is built from rows read in its own
last transaction.

## 5. Tests

Red first, before the fix: the round-5 blocker and the three round-5 should-fix findings (plan
Appendix A).

Then, for each state (no intent; intent committed and never sent; request in flight; unclear
inside the window; unclear past the window; refused; account bound; account bound and a changed
declaration; an account of another platform or mode) and each writer (PATCH changing the country,
PATCH switching euros off, PATCH that changes nothing, a DZD-only change, the single-currency
POST, onboarding, onboarding from a second device, a ban, a role change, an email unconfirmed by
staff): the answer code and the rows afterwards.

- **Property:** every action a GET offers is accepted by its write, or refused only with
  `payout_preference_changed`.
- **Real threads, both orders:** preference write and intent commit; two onboarding calls; a ban
  against the link handoff.
- **Crash points:** after the intent commit, after the request, after the record. Closing the
  database connection releases nothing that matters.
- **The listing:** no page; a match on the second page; no match on a complete listing, then the
  fresh attempt creates; two matches; an error on the second page.
- **One answer:** a commit between two of a GET's reads does not split the response.

Mechanical checks: a scan test that no session-level advisory lock is taken in the payout setup
path; a test gateway that fails when it is called inside a transaction.

The tests of the closed families (F-A, F-B, F-D, F-E) pass with the lock removed.
