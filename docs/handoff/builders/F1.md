## 4. What you build

Paths are under `backend/monolith/`.

**F-C1. The freeze** (`apps/finance/payout_profiles.py`, `set_preference`).
While `current_creation(method)` is prepared, committed or unknown, a write that would change the
euro method's `enabled` or its country is refused with the stable code `payout_setup_in_progress`
(409), translated. The check runs after `_method` returned the locked method row and before any
write. A write that changes neither, and any DZD write, is not refused. The PATCH and the
single-currency POST both call `set_preference`, so there is one check.

**F-C2. Who may still send** (`apps/finance/payout_accounts.py`, `_ask_stripe` and its callers).
Immediately before a create is sent, read the operation row again. Send only if it is still
outstanding, carries this call's fingerprint and is inside `IDEMPOTENT_REPLAY_SECONDS`. Otherwise
only retrieve or search, read the rows again, and answer from what is there now.

**F-C3. When the freeze ends.** A recorded and bound account ends it. A definite refusal with no
provider object ends it. An unknown outcome, or a search that found nothing, keeps it.
**[Guess]** Stripe refuses a repeated create of the same request the same way. Confirm it from the
adapter and Stripe's documentation of idempotent requests; if it does not hold, stop and ask.

**F-C4. Overlapping onboarding calls** (`_require_unchanged`, `_record_account`, `_bind`).

- `_require_unchanged` accepts the declaration the call planned for, and also its binding
  successor: a later version of the same method with the same country and an account, where every
  version in between is one too. `_bind_version` creates exactly these. A traveler's own change has
  no account on its version, so it breaks the chain and is still `payout_preference_changed`.
- A conditional update that changes zero rows means another caller got there first. Read the rows
  again and answer from them. Never answer "Finance required" or "preference changed" from what
  the call saw earlier.

**F-C5. The read model** (`stripe_setup_projection`, `onboarding_refusal`,
`payout_profile_api.py`, `payout_mobile.py`). While the freeze holds inside the replay window, the
euro options are not changeable, with `payout_setup_in_progress`, and "continue setup" is offered.
Past the window with nothing found (`stripe_account_unresolved`), "continue setup" is not offered
and the state is "waiting for support".

**F-F. Eligibility on the locked row.** One function answers "may this account write payout setup
now": active, not banned, a traveler role, a confirmed email. It replaces `holds_payout_setup`
plus the separate email checks in the views. It is evaluated on the user row that is locked first
(the `select_for_update(no_key=True)` that `_method` already takes, and the one in
`_plan_onboarding`), and again in the last transaction before the hosted link is returned. A
creation that was already committed when a ban arrives may still be recorded, so the account at
Stripe is known to the database. It is not bound and no link is handed out.

**F-G. One snapshot per response.** Each payout GET loads its facts (user, methods, versions,
standing account, creation, policy) inside one read-only `REPEATABLE READ` transaction, into plain
values. Serializers take those values and make no query. The two places that compute the euro
actions (`payout_profile_api.py` and `payout_mobile.py`) use the one set of facts. A write's
response is built from facts read in its own last transaction, under its locks. At the link
handoff the method's current version must be the planned one or its binding successor.

## Rules, the same for every builder

1. Build what this brief names and nothing else. Add no lock, counter, generation, flag, column,
   job kind or retry loop that the plan does not name. If one seems needed, stop and ask.
2. Red first. Reproduce each finding listed under "Tests" as a failing test before you fix it. A
   failing test must tell the bad outcome apart from a correct serial execution.
3. Group tests by family, in files named after the invariant. Never skip, delete or weaken a test.
   A test of a mechanism you delete is rewritten to the new rule, and the pull request lists it
   with the reason.
4. Remove what you replace in the same pull request. The tests of the closed families stay green.
5. The server enforces every rule. The app never fakes a result. Every user-facing string exists
   in English, French and Arabic.
6. After a migration, run `task check-drift` in `backend/` and commit the regenerated contract.
7. Push only to your branch, with ordinary pushes: no force push, no rebase of pushed commits. The
   whole suites and the Android build run in GitHub CI on the branch. While you fix, re-run locally
   only the tests that failed. The work is ready only when every CI check is green, "Schema drift"
   included.
8. Never deploy, never restart or change a server, never build the app for a device. The
   repository is public: no server address, account email, key, token or password in a file, a
   commit, the pull request or a comment.
9. Do not edit `HANDOFF.md`, the plan, or files that belong to another brief. Do not merge. Write
   nothing on GitHub except the pull request description.
10. No model name in a commit, a pull request or a document. Do not use the word "partner".
