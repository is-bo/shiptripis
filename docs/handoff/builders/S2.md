# Brief S2: a token refresh survives a lost answer

**Builder:** Claude Opus, extra-high effort.
**Branch:** new, from the tip of `main`, after N1 has merged. Server only.
**Read first:** `CLAUDE.md`; `docs/handoff/builders/README.md`; the plan
(`docs/handoff/LOOP_END_PLAN.md`) sections 3 and 6; the N1 phase document;
`backend/monolith/apps/accounts/sessions.py`.

## 1. Your job

Today the refresh token is rotated at every refresh and the old one is blacklisted
(`ROTATE_REFRESH_TOKENS`, `BLACKLIST_AFTER_ROTATION`). When the answer to a refresh is lost on a
weak network, the phone still holds the old token, presents it again, is refused, and the member
is signed out. A refresh happens every five minutes of use, so this will happen to real members.
It is the same on `main`.

## 2. What you build

Paths are under `backend/monolith/apps/accounts/`.

**The rule.** At most two refresh tokens of one sign-in are accepted: the current one, and the
one it was rotated from. The older one stops being accepted when the current one is used.

**The mechanism** (`models.py` `SignInSession`; `sessions.py` `SessionRefreshToken` and
`SessionTokenRefreshSerializer`).

- One new column on `SignInSession`: the `jti` of the token presented at the last successful
  rotation.
- A refresh locks the sign-in row. A token that is not blacklisted rotates as today, and its
  `jti` is stored in the column. A token that is blacklisted is still accepted when its `jti`
  equals the column: it gets a fresh pair, and the column does not change.
- Any other blacklisted token is refused, as today. A sign-in that has ended refuses every
  token, as today: the row's liveness is checked first.
- Add no time window and no setting.

## 3. What is not yours

The phone: it needs no change, because it already repeats the refresh with the token it holds.
Sign-out, password reset and the push rules (N1).

## 4. Tests

Red first: a refresh whose answer is dropped, then the same token again: today 401.

- The lost answer, once and twice in a row: each repeat gets a working pair.
- After the phone used the new token, the older one is refused.
- A token two rotations old is refused.
- Two refreshes with the same token at the same time: both get a working pair, and the row ends
  in one consistent state.
- A sign-out, a password reset and a ban each still end the sign-in: the current token and the
  older one are both refused afterwards.
- The access token's lifetime and the 30 seconds of leeway are unchanged.
