I recommend revising the plan before building because a conforming implementation could forget a live sign-in, release an order for a second payment, or restore authority that staff had removed.

## Contract

**Section 3.1 is usable for safety findings once it defines what counts as one fault.** A staff edit, a second tap, a retry, and a worker resuming are ordinary participants in an interleaving. A lost response and the retry it causes are one failure sequence. A provider outage affecting several polls is one outage. For recovery claims, assume the app or worker runs again and the dependency eventually answers. “The server always hears” is otherwise impossible under 3.1(b). I accept the exclusion of a configuration change racing an in-flight request. A new request made tomorrow against an unresolved intent and tomorrow’s configuration is expressly inside the model.

**I would change the following severity decisions.**

**Three lines are presently undecidable.** First, 3.1(j) excludes most two-fault cases that 3.2 calls “inside the model” and eligible for acceptance. It can also exclude a visible, irreversible privacy disclosure because someone can *see* it. Give M/A/C precedence for a demonstrated breach, including a coupled failure sequence. Apply L when neither an app path nor a named, authorized staff action restores service. Then apply Accepted risk only to a named, evidenced, repairable non-blocker. A “sub-second window” needs an actual bound. Staff repair needs an executable action and an observable successful result.

Second, **C needs a time boundary**. Local sign-out can immediately remove local authority. Remote revocation can be outstanding while offline, must survive restart, and must converge after connectivity returns. Specify the treatment of already-issued access JWTs and authenticated sockets. N1 deliberately allows an issued access token to its expiry, with clock leeway. The current wording makes that a standing blocker even after successful server sign-out. Continuing refresh, new registration, or delivery of private information to another member remains C or A. [N1 session contract](https://github.com/is-bo/shiptripis/blob/3e7fc1780878b3e017a9dd9f921a90774346142b/backend/monolith/apps/accounts/sessions.py#L12)

Third, **“outside the families” does not decide scope**. Apply the owner’s comparison with `main`. An unchanged independent fault gets a follow-up. A new failure introduced by a planned mechanism, including a shared runner or model override, is a plan or build gap even if its family was omitted. For an in-model observation with no wrong result, record no finding.

**I can work within one full pass and one re-check.** The first prompt must pin the approved plan revision, owner decisions, merge base, code head, and dependency heads. It must supply the entire package diff, the old reports, the writer and caller inventory, the state/event matrices with expected outcomes, red/green evidence, tests removed or rewritten and why, and exact-head CI and applicable device evidence. For transferred findings, use the rejected branch where the behavior exists for the red test, then exercise the integrated public entry point for green. An S1 test on `main` cannot by itself reproduce a P3B moderation gesture on a screen absent from `main`.

Round two covers the fixes and their affected callers. Stop with the owner if either a Blocker **or a rejecting Should-fix** remains. Section 3.2 rejects both, while 3.4 specifies a stop for only one. Switching a feature off is an option only if the switch makes the reported sequence unreachable, including shared writes and background jobs.

- **Extract S1, with a server prerequisite.** One member boundary is a sound replacement for per-screen account checks. S1 as specified misses second engines, server-session revocation, callbacks into the surviving core, and notification delivery outside Flutter. ## Decisions D4 and D5

**D4(a) is safe. D4(b) needs new wording.** “Keep collection blocked while a reported debit is unresolved. Credit a verified, applicable payment exactly once. Preserve the existing unapplied-payment and refund path where it cannot be applied. Staff may release the order only on affirmative evidence that the checkout cannot collect and no debit remains outstanding, or on an audited disposition accounting for the debit. An unreadable, open, processing, mismatched or ambiguous answer leaves the hold in place. A subsequent verified payment on a resolved item creates a durable, deduplicated Finance obligation with a named disposition. Automatic paths respect the recorded decision.” Capture the provider reference, evidence, reason, actor and disposition. An HTTP-successful read alone authorizes nothing.

**D5’s freeze is safe with a defined release condition.** “While creation for the current platform and mode can still produce an account, refuse an effective EUR country or enablement change through either preference endpoint. Keep unrelated DZD changes and genuine EUR no-ops available. Release after a safely recorded binding or definitive no-object outcome that no outstanding dispatch can reverse. For unknown or search-miss outcomes, advertise only actions that can actually advance the case, including the authorized Finance route. Preserve funded instructions.” In particular, do not show **Continue setup** in a state where onboarding deterministically returns `stripe_account_unresolved`.
