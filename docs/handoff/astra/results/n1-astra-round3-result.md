**Checked and found sound.** I accept the decision on round-2 blocker 1. Requiring `binding_sequence` for registration follows the repository’s explicit old-client rule. The unnumbered sign-out finding above affects the **current** app’s own fallback. For ordinary numbered operations, the installation lock covers the sequence claim and device mutation in one transaction. A lower registration is refused, a newer numbered sign-out can precede first registration, and a late or low sign-out deactivates an existing device belonging to its own `sid`. Registration and account-wide push deactivation take the user lock first. The ordinary 409 catch-up makes at most one additional registration.

On the phone, installation-ID creation is serialized through the real `TokenStore` queue. First-open waits for first paint, messaging initialization, session resolution, and a usable foreground route. The sign-in transition test checks the outgoing widget **at dispatch**. Startup and Profile share an in-flight dialog. A failed automatic count write prevents dispatch, and missing or failed Firebase initialization spends nothing. The documented process-death window between the durable write and native dispatch can still suppress an unseen Android prompt.

I checked the pinned Android plugin’s fresh-install, rationale, and permanent-denial mappings, the below-33 path, the first-dismissal recovery, and the iOS undetermined, provisional, and authorized paths. A Settings grant reconciles on resume. Guests load no account preferences and register only after grant and sign-in. Both registration-retry tests again use HTTP 500 and assert recovery without a second prompt. The handover test retains its exact storage-key allowlist, and the two added counters contain only integers. The changed copy exists in EN, FR, and MSA and retains “Wassla” in Latin script.

**Verification limits.** I inspected all 18 supplied 360 px English and Arabic screenshots and saw no notification control clipped or covered by bottom navigation. The 320 px RTL layout, required real Android 13+ dialog capture, and physical iOS reinstall behavior remain unverified. I did not run Flutter, PostgreSQL, or mutation tests under the read-only constraint. GitHub returned no PR workflow runs or commit statuses for the pinned SHA. The reset test uses sequential requests, so it supplies no independent evidence of concurrent lock behavior.
