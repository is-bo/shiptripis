### What I checked

- **Scope.** I fetched `origin`, compared the three-dot package diff against `origin/main`, and inspected `bd74c3a` separately. The three later commits through `eceb4f8` change only `docs/handoff/astra/f1-review-round5.md` and `docs/handoff/status/F1.md`.
- **Lock order and lifetime.** I found no production EUR declaration writer bypassing the setup lock and no reversed acquisition. The PATCH already owns the lock when its inner EUR write reacquires it. On a healthy connection, each nested session acquisition has one unlock in `finally`, including on provider exceptions. PostgreSQL releases all counts when the session ends. The blocker arises because the web thread can outlive that session. [financial_locks.py:347](https://github.com/is-bo/shiptripis/blob/bd74c3a8048ad0e0e0abb2be94e72883ce8ac6c5/backend/monolith/apps/core/financial_locks.py#L347)
- **Waiting.** The onboarding holder keeps no business row lock across Stripe I/O. A waiting preference write has an open transaction but takes no `User`, method-set, method or account lock before its initial setup wait. Funding, refresh and webhooks can acquire their normal locks. The shared resource at risk is web capacity. The 3.05 s connect and 15 s read defaults apply per provider request. Gunicorn’s 120 s `gthread` setting and PostgreSQL’s idle-in-transaction timeout do not put a deadline on an active advisory-lock wait.
- **Money and actions.** I found no cross-traveler binding, second Stripe account, changed-body replay or change to a funded instruction from the traced paths. A current creation inside the window reuses its key and body. Superseded or expired creations are searched by operation reference. For stable states, the standing-account, country and environment checks agree with the advertised setup flow. A bound account can still be refreshed or managed after its country closes, as specified. [payout_accounts.py:577](https://github.com/is-bo/shiptripis/blob/bd74c3a8048ad0e0e0abb2be94e72883ce8ac6c5/backend/monolith/apps/finance/payout_accounts.py#L577)
- **Tests and limits.** All four thread tests require an ungranted advisory lock on the exact two-part key and identify the leader through `pg_blocking_pids`. A row-lock wait or removal of setup locking would fail that assertion. All preference races use PATCH, so removing only the single-currency POST’s lock would escape them. Worker cleanup closes connections, so the suite also does not establish cleanup on persistent-session reuse. The five same-connection tests retain their guard assertions. I used the supplied green PostgreSQL 16 CI result and reviewed source only. I did not rerun tests, inject a connection failure, or call Stripe.
