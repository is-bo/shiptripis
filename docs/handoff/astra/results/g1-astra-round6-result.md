**Other verification.** The checkout endpoints store the session ID before returning the URL. I found no ordinary payer path that could complete an app-issued checkout before that commit, no checkout-provider HTTP call under a database lock in the traced entry points, and no double application from concurrent reconciliation of a correctly bound, matching capture. The aggregate lock, succeeded-attempt check and stable refund key protect that case. A lost Chargily create response can still leave an open provider object whose URL was never delivered, so the literal count of open provider objects can also exceed one without exposing two URLs to payers.

Provider failures back off after re-arming. I found no fail-and-re-arm loop on every worker cycle for those failures. The sweep arms at most 100 missing jobs per cycle, so the 101st live checkout can remain unarmed beyond one cycle. The guest state exposes only `ready` and `in_progress`, and the waiting and refresh copy exists in English, French and Arabic.

I compared the listed test rewrites against their prior assertions. The metadata removals, settlement and order-closure expectations, exact guest allowlists, and Flutter wait-state changes follow the new rules. The replay test no longer exercises a previously bound durable row, and the Stripe decline test loses the diagnostic assertion identified above.

**What I could not check.** This was a read-only review of `a0b48be..4e4c0ea` and the full three-dot package from merge base `18d9c96`. I did not independently run PostgreSQL, Flutter, Caddy, live provider transactions, a deployed phone flow, or the 16 mutations. Both exact-head workflows completed successfully.

Overall verdict: reject
