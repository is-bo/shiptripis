## What round 5 changed (detail: "Round 5" in `docs/PHASE_F1_PAYOUT_AVAILABILITY.md`)

Root cause: round 4 checked the declaration only while each short onboarding transaction held the
method lock; between them onboarding talks to Stripe with no lock, and a preference change could commit
there (after the account-creation intent and before its POST, during a second call's platform check,
during the link mint).

- `apps/core/financial_locks.py`: `hold_payout_account_setup(traveler_id)` (session-level advisory lock,
  key `PAYOUT_ACCOUNT_SETUP_LOCK = 51420302`) and `lock_payout_account_setup(traveler_id)` (same key,
  transaction level). Docstring of the canonical order updated.
- `payout_accounts.py`: `start_onboarding` and `ensure_account` hold the setup lock from reading the
  declaration to handing out the link. `ensure_account` refuses a closed rail (no country open) first.
  A creation's answer is dated by the operation's first request. The link check compares the exact
  version the account was resolved on. New `destination_account(actor)`, used by refresh and dashboard,
  refuses an account outside the configured platform and mode before Stripe. An accepted creation
  clears `provider_object_status`.
- `payout_profiles._method` (EUR) and the PATCH view take `lock_payout_account_setup` before User.
- `payout_account_api.ConnectView._account` uses `destination_account`.
- Tests: new `apps/finance/tests/test_f1_payout_account_setup_race.py` (four real-thread PostgreSQL
  tests); in `test_phase8fh6a_mobile.py` the readiness test is rewritten, a new FR-DE-FR test, the
  link test gains an "away and back" case, the precedence, replay and platform tests are extended, and
  five same-connection guard tests are relabelled (assertions unchanged).
- PR #69 description is updated for round 5 (rewritten tests, checks, gate notes).

## Things to know before touching it

- Local test setup used: `service postgresql start`, a `shiptrip` superuser role and database, and the
  CI environment variables (`DJANGO_SETTINGS_MODULE=config.settings.dev` and the rest from
  `.github/workflows`). The real-thread tests need PostgreSQL; they skip elsewhere.
- A preference change sent while an onboarding call runs now waits for it (normally well under a second,
  at worst one onboarding call's Stripe timeouts). If that call bound an account, the change then fails
  its revision check (400 `payout_profile_invalid`); the app refetches. The F2 handoff in the phase record
  says so.
