Branch `claude/s1-session-core`, one pull request for both briefs. Briefs:

## State in one line

S1-A is built and handed back: the session record, its one writer, the one way in and out, the
sender and the account's one owner. S1-B starts from this branch's head once its CI is green.

## What S1-B finds in place

- `SessionCore` (`mobile/lib/core/session/session_core.dart`) is created in `main()` and reaches
  the app only through `sessionCoreProvider`, which `main()` overrides. `AppLifecycleListener`
  in `main()` calls `resumed()`. Design: `docs/PHASE_S1A_SESSION_CORE.md`.
- Every mutating call already names its sign-in: `end(sid, ...)`, `replaceTokens(sid, ...)`,
  `updateAccount(sid, ...)`; `signedIn` takes the reserved `SignInAttempt`. A call for a `sid`
  that is no longer current changes nothing.
- `SessionController.signOut()` and `accountDeleted()` end the sign-in current when they run.
  S1-B binds them to the sign-in their screen was built for (brief: "A's delayed account-deletion
  or sign-out completion after B signed in changes nothing").
- The API client takes the bearer only from `accessFor(sid)` for the `sid` current when the call
  started, refuses a request of an ended sign-in with "session changed" (a cancelled
  `ApiException`), and is still one client for the app (`apiClientProvider` watches the core).
  S1-B moves it into the member's container, one per sign-in.
- `core.busy` is the one busy state; the sign-in and sign-up screens and `SocialSignIn` do not
  read it yet and keep their own flags. `SessionNotSaved` has its translated copy in
  `describeFailure` and the Profile sign-out shows it; the password sign-in and sign-up screens
  catch only `ApiException`, so there it is not shown yet (the social buttons show their generic
  failure). Both are S1-B's.
- Sockets take their token from `accessFor(session.sid)` (`push_coordinator.dart`).

## For the tests

- `test/support/fake_api.dart`: `MemoryStorage` (read and write errors and gates), `coreFor`,
  `signInFor`, `signedInRecord`, `signInAnswer`, `fakeToken`. `FakeBackend.session` is the core a
  container uses by default (signed in as `sid-a`).
- In a widget test, launch with `launchPumped(tester, container)`, never inside
  `tester.runAsync`: the core's queue would then end on a real-time future, and the next write
  under the fake clock waits on it for real time.
- `pumpApp`'s default container has no `sessionCoreProvider` override; a bare widget test that
  reads the session needs one (S1-B's harness change replaces this).
