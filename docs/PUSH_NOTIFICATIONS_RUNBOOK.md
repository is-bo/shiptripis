# Push notifications architecture and activation

Phase 8F-D keeps the in-app `Notification` row as the source of truth. Push
is only a delivery channel:

```text
Django business commit
  -> Notification row + Redis pub/sub (same event_id)
  -> active notification WebSocket
  -> notif:fcm durable Redis stream
  -> 2 second grace + delivered:<event_id>:<user_id> check
  -> Firebase multicast when that user was not reached by WebSocket
  -> notif:fcm:results -> Django device success/invalid-token cleanup
```

Redis or FCM failure never rolls back the business transaction. The Go
consumer uses `XREADGROUP`, `XAUTOCLAIM`, bounded concurrency, retryable
pending entries, and a 45-second worker heartbeat. A permanent invalid or
unregistered token is acknowledged rather than poisoning the queue, then
deactivated by Django from durable feedback. `python manage.py
prune_push_devices --days 180` deactivates installations that stopped checking
in.

## Devices, APIs, and preferences

`PushDevice` is one authenticated user's app installation, not a hardware
identity. Its random UUID is generated by the mobile app and retained across
logout. A token is unique by SHA-256 fingerprint, an account may own multiple
devices, token rotation updates the installation in place, and rebinding the
same Firebase token transfers it to the currently authenticated owner.
Deleting the account cascades its devices and preferences. Sender feedback
carries the device row ID plus that fingerprint, so a delayed failure for an
old token cannot disable a newly rotated token on the same row.

- `POST /api/notifications/devices` registers/upserts the authenticated
  installation. The client cannot provide a user ID and the response omits the
  token and fingerprint.
- `POST /api/notifications/devices/unregister` disables only the caller's
  installation. Logout attempts this before clearing credentials, but logout
  succeeds offline; a later login safely rebinds the installation.
- `GET/PATCH /api/notifications/preferences` controls `messages` and
  `marketplace` across all devices. Essential payment, delivery, dispute,
  verification, and account-security pushes have no fake off switch.

Raw tokens are limited to the registration boundary, the encrypted transport,
the database sender query, and the internal FCM stream. Logs and admin use row
IDs or truncated fingerprints. Never add handover codes, exact private
locations, KYC documents, provider identifiers, evidence, or message contents
to push display text or data.

## V1 push matrix

| Category | Events | Android channel | Destination |
|---|---|---|---|
| Marketplace | `parcel.created`, `offer.created`, `offer.updated` | Deliveries | request or match |
| Essential | `parcel.cancelled`, `offer.accepted`, `deal.cancelled` | Deliveries | request, match, or deal |
| Essential | `payment.captured`, `payment.failed`, `payment.refunded`, `payout.status_changed` | Payments | deal or payouts |
| Essential | `match.in_transit`, `match.completed`, `handover.confirmed`, `handover.delivery_code_available`, `handover.delivery_confirmed` | Deliveries | deal |
| Essential | `kyc.status_changed`, `flight_proof.status_changed` | Account | KYC or journey |
| Essential | `dispute.opened`, `dispute.resolved` | Deliveries | dispute or deal |
| Messages | `chat.message.new` | Messages | conversation |

All display copy is selected in Django at publication time from the user's
authoritative EN/FR/AR communication language. Marketplace and chat entries
use FCM collapse keys to coalesce offline bursts; essential lifecycle events
do not. `match.created` is not separately pushed when the same action creates
an `offer.created` event. Journey self-publication/edit, rating availability,
and the protection-ending reminder remain in-app/email lifecycle behavior
until they have a distinct action-worthy V1 publication boundary.
`handover.code_issued` is never eligible for push because that event may carry
code plaintext.

Push data contains only an event ID, the recipient's notification row ID, and
allowlisted positive entity IDs. A tap while signed out goes to sign-in with a
local protected `next` path; the destination API still performs normal object
authorization. Foreground Firebase presentation is disabled, so it refreshes
inbox/chat state without a duplicate OS banner. Background and terminated-app
taps use the same structured routing table. The authoritative unread count is
always fetched from Django.

## Live client state (Phase 8F-F4)

While signed in and foregrounded, Flutter connects to both `/ws/notifications`
and `/ws/chat`. WebSocket and foreground FCM events share one session-bound
event-to-resource map. Events identify the affected Deal, Match, offer list,
request, journey, payment, dispute, payout or conversation; mounted providers
refetch their normal HTTP endpoints. Lifecycle and financial state remain
server-authoritative. Rapid invalidations coalesce, and duplicate event IDs
from both transports do not trigger the same resource twice.

Chat inserts a pending bubble immediately, then replaces it with the message
returned by the send endpoint. HTTP history and live reconciliation merge by
server message ID. Initial history reads the latest 50 messages; reconnect
fetches missed messages in pages of at most 200 using `after_id`, and scrolling
back uses `before_id`. The HTTP cursor never advances solely from a send ACK.
The history API retains legacy page reads and only marks returned incoming
messages as read. An additive `(match_id, id)` index supports these reads.

On foreground resume or socket reconnect, the client reconciles the current
route, mounted collections and unread count. It does not fetch unrelated chat
histories or every cached detail. Logout/account changes close sockets, discard
queued events and pending chat state, and reject stale session callbacks.
Account-keyed HTTP caches also prevent prior-account data from surviving into
the next account's loading or error state.

V1 proposal/counter/accept, pending cancellation/expiry, recipient setup,
pickup, code availability, delivery, completion and payout settlement now
publish refresh identities after the transaction commits. `deal.updated` is a
neutral in-app/WS refresh for changes such as recipient setup or payment-grace
expiry; it has no FCM display entry. A traveler's code-availability refresh uses
this neutral event, while the sender keeps the existing code-ready event.
No new event fields contain codes, private addresses, evidence, message text,
payment credentials or provider identifiers.

For regression QA, keep a conversation or Deal open on each party's device:
send/receive, confirm pickup, reconnect after missing several messages, then
background/resume and switch accounts. Check the visible state against HTTP,
including unread counts and eligibility, without navigating away and back.

## Android, iOS, and client configuration

Android has four normal-importance channels: Messages, Delivery updates,
Account and verification, and Payments and payouts. The operating-system
permission is requested on the app's own, once per installation, the first time
the app is open on a usable screen (decision of Ismail after the 2026-11-26
phone test): after the first frame and Firebase's start, with the app resumed
and the session resolved, whether or not the person has signed in, and never
over the splash, a sign-in or payment screen, or a notification still being
opened (it waits for the next screen). Sign-in, resume and preference changes
never display the prompt again. The installation keeps a count of the requests
it made, which survives logout and account changes, because Android 13 and newer
report a permission that was never asked for as a plain denial or as
undetermined, and the pinned plugin writes its own history only after the dialog
is answered; on Android the prompt goes ahead only while the status is
undetermined and that count is zero. A requestable denial is never asked on its
own: after an upgrade from a build that asked from Profile, Android reports that
one denial as requestable with no count on this installation, and that person
must not be asked again. The count is written to disk before the system is asked
and the prompt is skipped if it cannot be written. An app killed between that
write and the dialog counts a prompt that never appeared (Profile still asks).
iOS asks when the status is undetermined (its status is exact, and a reinstall
resets it) and respects authorized and provisional. Android below 13 has no
runtime prompt. A missing Firebase configuration or a failed start asks nothing
and spends nothing, so the next launch that can ask still does. A request the
system never received (the person left the app, the call failed) is taken back.
The prompt waits until the screen that was on top has finished leaving.

Profile > Notifications is the recovery path and the only later request, for a
guest as well (guest Profile has the row). On Android a requestable denial keeps
Enable; Settings is offered when the system reports a permanent denial. One
case is ambiguous: a first dialog swiped away denies nothing, so Android has no
rationale to offer and the plugin reads it as permanent. One request on record
with that reading therefore still offers Enable; a second swipe-away reads as
permanent, because Android cannot tell it from two denials. A permanent denial,
an older Android version whose notifications are disabled, or an iOS denial
links to the app's system notification settings. Returning from settings
refreshes the displayed permission state and registers the phone if it was
granted there. The first-open prompt, a resume and the Profile button share one
request, so the system is never asked twice at once; the Profile button asks
only while the app is in the foreground. A denial does not disable the app or
its in-app inbox.

The phone registers to an account only after sign-in. The app numbers every
registration and every sign-out of an installation from one counter (created
once, so one phone has one installation ID), and the server applies them in that
order (`PushInstallationBinding`): a registration overtaken by a later one, or a
number reused for a different request, is refused
(`409 push_registration_superseded`); a stale sign-out still ends the device
that belongs to its own sign-in. Every sign-in is a server row
(`SignInSession`) named by the `sid` claim of each of its tokens, rotations
included. A sign-out ends its sign-in and switches off every device that sign-in
registered; a password reset (`end_all_sessions`) ends every sign-in of the
account. A registration, and a refresh, from a sign-in that has ended is refused
(`409 push_session_ended`, checked under the account row lock that ending a
sign-in also takes). A slow registration can therefore never rebind the phone to
an account that signed out, was replaced or was reset.

Sign-out cleanup stays best-effort: a sign-out made offline never reaches the
server, so that phone keeps receiving the account's notifications until it signs
in again (its registration replaces the binding) or the account's sessions are
ended.

The permission state and ShipTrip notification-type preferences are separate.
Preferences control Messages and Marketplace delivery across the account;
they cannot grant the OS permission, and essential lifecycle notifications
remain enabled. After a grant, the client registers the Firebase token through
`POST /api/notifications/devices`. The screen distinguishes an incomplete
Firebase build, Firebase initialization failure and device-registration
failure; only the last offers an in-app retry. Never log or render the token.

The mobile build supplies public Firebase client identifiers with Dart
defines: `FIREBASE_API_KEY`, `FIREBASE_PROJECT_ID`,
`FIREBASE_MESSAGING_SENDER_ID`, and `FIREBASE_ANDROID_APP_ID`; iOS also needs
`FIREBASE_IOS_APP_ID` and optionally `FIREBASE_IOS_BUNDLE_ID` (default
`eu.wassla.app`, the app id on both platforms). An incomplete tuple leaves
push unavailable without affecting the app. These are Firebase client
identifiers, never Firebase Admin credentials. No `GoogleService-Info.plist`
or `google-services.json` is used.

On iOS the Runner is signed with `aps-environment` in every build (both
entitlements files, `ios/Runner/Runner.entitlements` and
`ios/Runner/RunnerAppleSignIn.entitlements`; "development" in the files, the
production value comes from the App Store profile) and `Info.plist` declares
the `remote-notification` background mode; `tools/check_ios_config.py` fails
CI if either disappears. `firebase_messaging` registers with APNs itself and,
with Firebase's default method swizzling, hands the APNs token to Firebase, so
`AppDelegate.swift` needs no push code. What remains outside the repository:
the App ID's Push Notifications capability, an App Store profile made after
it, and the APNs authentication key uploaded to the Firebase project
(`docs/WASSLA_SETUP_FOR_ISMAIL.md`, section 10). Do not claim iOS push
verification before a physical iPhone has received one.

## Post-pickup protection state (Phase 8F-F5)

After pickup, Deal, pickup and delivery surfaces render the server-provided
`delivery_code_available_at` during the 30-minute safety period. They explain
the wait in role-specific terms and show no delivery action until the server
sets `can_reveal_delivery_code` for the Sender or
`can_submit_delivery_code` for the Traveler. A countdown is explanatory only:
at its boundary the client refetches, and a live
`handover.delivery_code_available` event can trigger the same authoritative
refetch earlier. The client never derives permission from local time.

After delivery confirmation, the same surfaces show the server-provided
`protection_ends_at` and payout/protection status without an obsolete delivery
CTA. Completed Deals likewise expose no handover action. The Traveler never
receives or renders the delivery code, and none of these timestamps weaken the
existing code-privacy or payout-hold rules.

## Safe activation and operations

Keep `FCM_ENABLED=false` until all of the following are true:

1. The mobile Firebase project/app IDs and backend project ID match.
2. A Firebase Admin service-account JSON is privately mounted at
   `FCM_CREDENTIALS_PATH`; it is not in source control or the app bundle.
   On the VPS the credential is supplied base64-encoded in the secret document
   as `FCM_CREDENTIALS_JSON_BASE64` and `infra/vps/launcher.py` writes it to
   `FCM_CREDENTIALS_PATH` (default `/tmp/shiptrip/firebase-admin.json`, mode
   `0600`) before any child starts, then removes the encoded value from the
   environment so no worker inherits the payload. A credential whose
   `project_id` disagrees with `FCM_PROJECT_ID` refuses the boot.
3. `FCM_PROJECT_ID`, `FCM_STREAM`, `FCM_RESULTS_STREAM`, consumer groups, and
   stable consumer names are configured.
4. A test installation has registered a real token.
5. CI is green and the exact reviewed SHA is deployed.

Admin deep health distinguishes disabled, incomplete, configured, and
degraded states. When enabled it reports only safe aggregates: active-device
count, heartbeat-backed worker status, stream length, lag, and pending count.
Treat a missing heartbeat or growing pending/lag as degraded; configuration is
not liveness.

For activation, publish one controlled test event and record separately:
in-app row creation, FCM stream entry, worker heartbeat/consumption, Firebase
acceptance, and physical receipt. Firebase acceptance is not proof that a
phone displayed it. Never use a real handover/payment secret in this test.
