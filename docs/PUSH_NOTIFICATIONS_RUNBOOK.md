# Push notifications architecture and activation

Phase 8F-D keeps the in-app `Notification` row as the source of truth. Push
is only a delivery channel:

```text
Django business commit
  -> Notification row + Redis pub/sub (same event_id)
  -> active notification WebSocket
  -> notif:fcm durable Redis stream
  -> 2 second grace + delivered:<event_id>:<user_id> check
  -> Firebase multicast when that user was not reached by WebSocket
  -> notif:fcm:results -> Django device success/invalid-token cleanup
```

Redis or FCM failure never rolls back the business transaction. The Go
consumer uses `XREADGROUP`, `XAUTOCLAIM`, bounded concurrency, retryable
pending entries, and a 45-second worker heartbeat. A permanent invalid or
unregistered token is acknowledged rather than poisoning the queue, then
deactivated by Django from durable feedback. `python manage.py
prune_push_devices --days 180` deactivates installations that stopped checking
in.

## Devices, APIs, and preferences

`PushDevice` is one authenticated user's app installation, not a hardware
identity. Its random UUID is generated by the mobile app and retained across
logout. A token is unique by SHA-256 fingerprint, an account may own multiple
devices, token rotation updates the installation in place, and rebinding the
same Firebase token transfers it to the currently authenticated owner.
Deleting the account cascades its devices and preferences. Sender feedback
carries the device row ID plus that fingerprint, so a delayed failure for an
old token cannot disable a newly rotated token on the same row.

- `POST /api/notifications/devices` registers/upserts the authenticated
  installation. The client cannot provide a user ID and the response omits the
  token and fingerprint.
- `POST /api/notifications/devices/unregister` disables only the caller's
  installation. Logout attempts this before clearing credentials, but logout
  succeeds offline; a later login safely rebinds the installation.
- `GET/PATCH /api/notifications/preferences` controls `messages` and
  `marketplace` across all devices. Essential payment, delivery, dispute,
  verification, and account-security pushes have no fake off switch.

Raw tokens are limited to the registration boundary, the encrypted transport,
the database sender query, and the internal FCM stream. Logs and admin use row
IDs or truncated fingerprints. Never add handover codes, exact private
locations, KYC documents, provider identifiers, evidence, or message contents
to push display text or data.

## V1 push matrix

| Category | Events | Android channel | Destination |
|---|---|---|---|
| Marketplace | `parcel.created`, `offer.created`, `offer.updated` | Deliveries | request or match |
| Essential | `parcel.cancelled`, `offer.accepted`, `deal.cancelled` | Deliveries | request, match, or deal |
| Essential | `payment.captured`, `payment.failed`, `payment.refunded`, `payout.status_changed` | Payments | deal or payouts |
| Essential | `match.in_transit`, `match.completed`, `handover.confirmed`, `handover.delivery_code_available`, `handover.delivery_confirmed` | Deliveries | deal |
| Essential | `kyc.status_changed`, `flight_proof.status_changed` | Account | KYC or journey |
| Essential | `dispute.opened`, `dispute.resolved` | Deliveries | dispute or deal |
| Messages | `chat.message.new` | Messages | conversation |

All display copy is selected in Django at publication time from the user's
authoritative EN/FR/AR communication language. Marketplace and chat entries
use FCM collapse keys to coalesce offline bursts; essential lifecycle events
do not. `match.created` is not separately pushed when the same action creates
an `offer.created` event. Journey self-publication/edit, rating availability,
and the protection-ending reminder remain in-app/email lifecycle behavior
until they have a distinct action-worthy V1 publication boundary.
`handover.code_issued` is never eligible for push because that event may carry
code plaintext.

Push data contains only an event ID, the recipient's notification row ID, and
allowlisted positive entity IDs. A tap while signed out goes to sign-in with a
local protected `next` path; the destination API still performs normal object
authorization. Foreground Firebase presentation is disabled, so it refreshes
inbox/chat state without a duplicate OS banner. Background and terminated-app
taps use the same structured routing table. The authoritative unread count is
always fetched from Django.

## Android, iOS, and client configuration

Android has four normal-importance channels: Messages, Delivery updates,
Account and verification, and Payments and payouts. Android 13 permission is
requested only from Profile > Notifications after explanatory copy. A denial
does not disable the app or in-app inbox, and that screen links to system
notification settings.

The mobile build supplies public Firebase client identifiers with Dart
defines: `FIREBASE_API_KEY`, `FIREBASE_PROJECT_ID`,
`FIREBASE_MESSAGING_SENDER_ID`, and `FIREBASE_ANDROID_APP_ID`; iOS also needs
`FIREBASE_IOS_APP_ID` and optionally `FIREBASE_IOS_BUNDLE_ID`. An incomplete
tuple leaves push unavailable without affecting the app. These are Firebase
client identifiers, never Firebase Admin credentials.

The device model and Dart layer support iOS, but production iOS push is gated
on the Firebase iOS app, APNs key, Xcode push/background capabilities, signing,
and physical-device verification. Do not claim iOS verification before those
steps pass.

## Safe activation and operations

Keep `FCM_ENABLED=false` until all of the following are true:

1. The mobile Firebase project/app IDs and backend project ID match.
2. A Firebase Admin service-account JSON is privately mounted at
   `FCM_CREDENTIALS_PATH`; it is not in source control or the app bundle.
3. `FCM_PROJECT_ID`, `FCM_STREAM`, `FCM_RESULTS_STREAM`, consumer groups, and
   stable consumer names are configured.
4. A test installation has registered a real token.
5. CI is green and the exact reviewed SHA is deployed.

Admin deep health distinguishes disabled, incomplete, configured, and
degraded states. When enabled it reports only safe aggregates: active-device
count, heartbeat-backed worker status, stream length, lag, and pending count.
Treat a missing heartbeat or growing pending/lag as degraded; configuration is
not liveness.

For activation, publish one controlled test event and record separately:
in-app row creation, FCM stream entry, worker heartbeat/consumption, Firebase
acceptance, and physical receipt. Firebase acceptance is not proof that a
phone displayed it. Never use a real handover/payment secret in this test.
