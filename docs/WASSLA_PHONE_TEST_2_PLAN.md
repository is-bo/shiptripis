## 1. Findings

### 1.1 Guest payment — a privacy setting on the HTML form conflicts with Django's CSRF check

The shared link opens `GET /pay/guest/<token>`. The form posts to the same path and contains `{% csrf_token %}`. Django renders it with the request context. The three logged failures at 21:20:42, 21:22:15 and 21:22:51 reached this HTML route. The Flutter guest screen calls a different JSON checkout endpoint. A browser and an embedded browser can both produce the observed HTML request. The log's `actor_class` records whether Django recognized a user on the request. The payment handler explicitly passes `actor_id=None` in both cases. `config/urls.py:46–54`, `templates/payments/guest.html:36–38`, `apps/finance/guest_web.py:299–325,417–438,486`, `apps/core/middleware.py:40–47`, `apps/finance/urls.py:153–161`, `features/guest/guest_pay_screen.dart:91–101`.

The shared payment shell specifies `no-referrer` so the URL containing the bearer token stays private. In an isolated Chromium 154 test, submitting a same-origin HTTPS form with that exact meta policy sent **`Origin: null` and no `Referer`**. With `strict-origin`, the same test sent the site's origin in both headers. Django 5.1.4 checks a supplied Origin before examining the form token. `null` fails the origin check. If a browser omits Origin entirely on HTTPS, the missing Referer fails the fallback check. A valid hidden token and matching cookie do not rescue either request. The guest-page tests use ordinary `APIClient` submissions and explicitly require the privacy meta tag. `templates/payments/_shell.html:8–10,17–20`, `requirements.txt:1`, `config/settings/base.py:120`, `apps/finance/tests/test_j7c_guest_link_ux.py:346–370,441`. [Django 5.1.4 CSRF middleware](https://github.com/django/django/blob/5.1.4/django/middleware/csrf.py#L434-L469)

The public Caddy sets the forwarded scheme from the TLS connection, and the internal gateway forwards it to Django. Production trusts that header, uses Secure cookies and sets CSRF SameSite to Lax. The supplied trusted origin matches the public HTTPS host. The checked-in VPS cache rule covers static marketing routes. There is no evidence of a cached guest form, an incorrect Secure flag, a missing template tag or a required change to the host allowlist. The exact Django rejection reason, cookie presence and browser used in each historical request were unavailable. The Chromium test establishes a sufficient cause without attributing unobserved headers to the phone. `infra/vps/Caddyfile:22–35`, `infra/vps/gateway.Caddyfile:61–69,84–87`, `config/settings/prod.py:12–25`, `config/settings/base.py:589`.

**Decision for G1.** Preserve `no-referrer`. Make only the token-authorized guest HTML checkout independent of Django's cookie-based CSRF check. Django's default CSRF cookie is separate from the login session. Neither cookie supplies authority here. Possession of the unguessable, expiring, revocable link authorizes starting hosted checkout for one outstanding obligation. The server chooses the amount, validates the rail, binds the attempt to the order and grants no account, deal, chat or refund authority. The provider still requires the payer's action, and only verified payment processing can fund the order. Preserve these properties even when a signed-in member opens another person's link. `docs/SHIPTRIP_V1_SPEC.md:809–823`, `apps/finance/services.py:385–410,1276–1346,3116–3159`, `apps/finance/guest_web.py:373–395,417–456`.

**Classification:** reproducible web bug. The historical subreason remains unverified. There is no reason to trust `Origin: null` globally, widen trusted origins, weaken Secure cookies or change the proxies.

### 1.3 Payouts — history, method setup and money movement have different gates

**History.** Profile exposes both Payouts and Payout methods. `GET /api/payouts` returns the signed-in traveler's paginated earnings. `GET /api/payouts/<public UUID>` scopes the detail to the same traveler. History does not require Connect or payout profiles. An account with no earnings should get an empty list and a route to setup. Two real UI defects are visible in source. History fetches only page 1 of 50 and renders that page even if `next` exists. A detail needing setup looks for `configure_payout_method`, but the server supplies rail-specific actions such as `configure_dzd` or `resume_eur_setup`. The intended setup button can therefore disappear. Neither defect establishes what happened on the owner's particular history screen. `features/profile/profile_screen.dart:99–109`, `apps/finance/views.py:617–652`, `mobile/lib/app/app_state.dart:795–812`, `features/profile/payouts_screen.dart:46–88`, `apps/finance/payout_mobile.py:43–57,73–83,324,354–357`, `features/profile/payout_detail_screen.dart:270–278`.

**Methods.** `GET/PATCH /api/payouts/methods` reads the two methods and saves an explicit EUR-only, DZD-only or both preference using revision checks. The profile views require authentication, verified email for writes, and `PAYOUT_PROFILES_ENABLED`. With profiles off, the methods endpoint raises a plain 404. The app offers the page anyway and renders a generic error. An active traveler or dual-role member can write a method. A sender-only account seeing a setup action can reach a server refusal. The lead supplied the keyring state, but **did not supply the running value of `PAYOUT_PROFILES_ENABLED`, the tester's role or the methods response**. The example defaults to false. Verify the deployed value before diagnosing this phone. `apps/finance/payout_profile_api.py:135–151,194–237`, `apps/finance/payout_profiles.py:30–66`, `features/profile/payout_methods_screen.dart:214–242`, `infra/vps/stack.env.example:41–51`, `docs/WASSLA_DISCOVERY_PRO_PLAN.md:1892–1897`.

**EUR.** Hosted Stripe Connect onboarding, dashboard access and readiness refresh exist. With profiles on, Connect off and no countries, the summary returns `eur.supported=false`, no EUR actions and an empty country list. Direct onboarding returns `stripe_connect_unavailable` when the Connect gate is reached. The app still enables EUR-only and Both. On a fresh account those choices open a country dialog whose only action is Cancel. The EUR card describes setup from the method state without using the separate availability field. With Connect enabled, the app opens the server-issued hosted URL and refreshes on return. A browser return alone proves nothing about readiness or a bank payout. `apps/finance/payout_mobile.py:20–58`, `apps/finance/payout_accounts.py:162–199`, `apps/finance/payout_account_api.py:77–93,130–147,160–202`, `features/profile/payout_methods_screen.dart:57–100,104–124,138–195,307–330,420–434`.

**DZD.** The implemented manual method is the traveler's Algerian postal account. It takes first name, last name, CCP number, two-digit CCP key, 20-digit RIP and **a photo of the full crossed cheque**. The app uploads a multipart image to `POST /api/payouts/proofs`, then submits its reference and the profile revision to `POST /api/payouts/profiles/dzd`. The backend validates the image, ownership and purpose, encrypts the evidence and account fields, exposes masks and sends the profile for review. The review requires a legal-name check against approved ID. The traveler's cheque and Finance's later transfer receipt are separate documents. Neither generic bank RIB entry nor an optional-document route is implemented. V1 requires capability-based EUR and manual fallback. The finance contract supplies the concrete CCP/RIP workflow. `docs/SHIPTRIP_V1_SPEC.md:825–831,837–854`, `docs/PHASE8F_H6A_MOBILE_PAYOUT_CONTRACT.md:102–118`, `apps/finance/payout_profile_api.py:58–78,247–263`, `apps/finance/payout_evidence.py:19–41,46–94`, `apps/finance/payout_profiles.py:175–241`, `mobile/lib/data/repositories.dart:1640–1683`, `docs/ADMIN_OPERATIONS.md:358–371`.

There is a second setup trap. The DZD card sends a new traveler directly to the upload form. Submitting a document creates a reviewed-version candidate but does not enable the currency preference. A new method defaults to disabled, and the summary projects it as `inactive` even after submission. That distinction is valid for money routing. The app needs to explain it and offer the explicit preference choice. It must not silently move a traveler from EUR to DZD or from EUR-only to Both. The form also reads the latest revision *after* uploading, which can defeat the user's protection against replacing something changed since they opened the form. `features/profile/payout_methods_screen.dart:625–660`, `features/profile/dzd_setup_screen.dart:144–179`, `apps/finance/models.py:1031`, `apps/finance/payout_profiles.py:49–66,229–252`, `apps/finance/payout_mobile.py:61–97`.

**Money boundary.** Incoming Stripe and Chargily test payments and the configured rate of 280 DZD/EUR do not enable outgoing payouts. Preferences apply to future funding. With both methods enabled the server selects the eligible currency by funding rail. Turning profiles on also changes deal-balance funding preflight. Preserve integer EUR cents, the server's frozen FX and destination, the funded arrival floor, 48-hour protection and dispute freeze. `apps/finance/payout_snapshots.py:62–103`, `docs/WASSLA_DISCOVERY_PRO_SPEC.md:85–93`, `docs/PHASE8F_H6A_MOBILE_PAYOUT_CONTRACT.md:33–54`.

**Classification:** Connect onboarding is switched off. Profile and private-store activation are unverified operations prerequisites. The dead choices, lost setup action, first-page-only history and unclear DZD preference flow are code defects. General bank/RIB support would be new money scope.

### 1.4 Route alerts — offering an alert and delivering an alert are separate user actions

**Offering one.** A signed-in member can manage alerts in Profile, choose trips or requests and two places, or follow a person's usual route. Browse already keeps canonical filters. When a filtered search is empty it offers to clear them. It does not offer to watch those cities. `features/profile/profile_screen.dart:117–127`, `features/discovery/alerts_screen.dart:93–100,203–252`, `features/discovery/person_screen.dart:257–303`, `features/discovery/browse_screens.dart:252–269,367–390`.

**Delivering one.** Posting an open request, opening it after the deposit, or publishing a journey schedules durable fan-out. The worker re-reads policy and listability, compares ordered served localities, honors person visibility and blocks, excludes the owner, and claims a six-hour quiet period per alert. Creation deduplicates active alerts and caps them at ten per member. A hit publishes `discovery.route_alert` to the member's bell and is eligible for marketplace push. A push or bell tap opens the relevant listing. An alert watches publication on a route. It does not promise the parcel passes all compatibility gates. `apps/parcels/views.py:536`, `apps/finance/services.py:904`, `apps/trips/services.py:290`, `apps/discovery/alerts.py:41–58,73–169,180–254`, `apps/discovery/models.py:21`, `apps/notifications/push.py:455,672–679`, `core/push/push_coordinator.dart:435,515–529`, `features/notifications/notifications_screen.dart:201–210`.

There is also an automatic **trip-fit alert** when a request opens. It uses the existing compatible-journeys ranking, picks a traveler's best qualifying trip and applies policy caps, normally 30 travelers per request and five per traveler per 24 hours. A traveler already told about the request is excluded from the route-alert fan-out for it. Marketplace preference controls eligible phone delivery. A bell row and a phone banner are independently observable. `apps/discovery/trip_fit.py:45–68,82–115`, `apps/discovery/alerts.py:91–119`, `docs/WASSLA_DISCOVERY_PRO_SPEC.md:161–173,460–474`.

**Classification:** a contextual invitation is missing UX. Notification on a qualifying new listing already exists. Live FCM is off, and the supplied facts do not identify a particular saved alert, qualifying new event or failed fan-out. Recommended default is one explicit offer after an empty two-city search, with the existing delivery system behind it.

### 1.6 Partial match — Algiers to Paris covers the flight, leaving Jijel to Algiers uncovered

V1 requires exact equality of canonical matching localities. A locality represents itself. An airport uses its active primary **served** locality. A preferred meeting point is within the selected locality. Preferred pins, a short distance or a plausible road connection cannot substitute for visiting it. The addendum permits a parcel to join at a pickup-enabled stop and leave at a later drop-off-enabled stop. “Covered legs” are the traveler's actual legs between those stops. Even the existing `excellent`, `good` and `compatible` labels all describe pairs that passed the full engine. `docs/SHIPTRIP_V1_SPEC.md:169–205,470–478,549–580`, `docs/WASSLA_DISCOVERY_PRO_SPEC.md:183–193`, `apps/matching/find_travelers.py:146–179`.

The reviewed catalogue maps ALG to Algiers and CDG to Paris. Their physical municipalities are separate catalogue relationships. Journey 11 therefore has matching nodes `[Algiers, Paris]`. Request 1 asks for `[Jijel, Paris]`. The Paris endpoint is served. The flight supplies no pickup at Jijel and establishes no first-mile journey. There is no active feature assigning that segment to the sender, the traveler or a courier. The unset route provider returns `UnavailableRouteProvider`. Straight-line fallback is irrelevant to this canonical flight. `tools/geography/airport_locality_mappings_2026.json:2–55`, `apps/matching/compatibility.py:144–167,423–441,476–493,827–835`, `apps/routing/providers.py:376–382`.

**What the owner sees.** Home matches and Find Travelers omit the pair. Either listing can still appear in ordinary Browse to another eligible viewer. Choosing the request against the trip in focused discovery explains the refusal. On the traveler's side “I can carry this” returns `409 incompatible_candidate`, records no interest and sends nothing to the sender. Today's app gives the misleading date explanation in 1.7. An actual published journey with a qualifying Jijel → Algiers leg followed by the approved flight could cover both endpoints. It must still pass the other gates. `apps/matching/discovery.py:649–658,784–793`, `apps/discovery/matches.py:48–75`, `apps/discovery/interest.py:35–42,55–82,96–106`, `features/requests/discovery_screen.dart:365–417`, `features/discovery/discovery_actions.dart:150–167`.

**Classification:** correct rejection as a full match. A visibly labelled alternative departure is missing product scope. The minimal extension is a browse-only option for a sender willing to reach a different departure city. It must never make the existing Jijel request actionable against the Algiers flight. See Q3 and M3.
